2. Cambiaría una cosa del apartado de "simular comportamiento humano"
Esta parte:
"delays aleatorios (...) para simular comportamiento humano"

yo la eliminaría como objetivo del sistema.
Podés tener rate limiting y espaciamiento entre mensajes, pero no diseñaría el sistema para intentar engañar a Meta.
Por ejemplo:
Mensaje 1
   ↓
esperar 15s
   ↓
Mensaje 2
   ↓
esperar 20s
   ↓
Mensaje 3
está bien como mecanismo de control de velocidad y protección del servicio.
Pero conceptualmente:
"simular comportamiento humano para evitar detección"

es una mala base para el sistema.
Además, 10-20 segundos implica que:
100 mensajes ≈ 17-33 minutos
500 mensajes ≈ 1h 23m - 2h 46m
1000 mensajes ≈ 2h 46m - 5h 33m
Para campañas pequeñas no importa demasiado, pero conviene que el sistema sea consciente de esto.

5. Haría que la campaña genere los mensajes inmediatamente
Cuando el usuario hace:
Crear campaña
el backend:
1. Crea campaña
2. Obtiene destinatarios
3. Crea scheduled_messages
4. Marca campaña como Pendiente
Por ejemplo:
Campaña #15

2.350 destinatarios

scheduled_messages:

#1
#2
#3
...
#2350
Después el Worker solamente procesa:
WHERE status = 'pending'
AND scheduled_at <= NOW()
Esto tiene una ventaja enorme: la campaña queda completamente registrada antes de comenzar a enviar.
6. No pondría el delay directamente en el cron
En lugar de pensar:
for (...) {
    await send()
    await sleep(random)
}
haría que cada mensaje tenga su propio:
scheduled_at
Por ejemplo:
Mensaje 1 → 20:00:00
Mensaje 2 → 20:00:17
Mensaje 3 → 20:00:31
Mensaje 4 → 20:00:48
Mensaje 5 → 20:01:03
Entonces el Worker simplemente consulta:
WHERE status = 'pending'
AND scheduled_at <= NOW()
ORDER BY scheduled_at
LIMIT 1
Eso hace que pausar una campaña sea trivial:
campaign.status = 'Pausada'
y el worker deja de procesarla.

y que el frontend espere indefinidamente.
